# Intelligent Heatwave Risk Prediction and Early Warning System

Use case KJS-CES-01 (Climate Intelligence for Heatwave Monitoring, Prediction, and Early Warning).
All data are **synthetic**: for teaching and demonstration only. Do not use this system for real-world warnings.

---

## Project overview

Heatwaves are among India's deadliest weather hazards, and warnings are only useful if they are early, local and
understood by the people who must act. This project is a working prototype of an end-to-end early warning system
for **10 Indian cities** (Delhi, Jaipur, Ahmedabad, Lucknow, Nagpur, Mumbai, Pune, Hyderabad, Chennai, Bhubaneswar),
grouped into 7 climatic regions.

Every evening the system:

1. cleans the day's observations,
2. forecasts the maximum temperature (Tmax) for the next 7 days, with a 90% range,
3. estimates the probability of each severity class (normal, hot day, heatwave, severe heatwave) using IMD-style rules,
4. converts the probabilities into a colour-coded alert (Green, Yellow, Orange, Red) and a 0-100 Heatwave Risk Index,
5. finds hotspot clusters, checks the forecast against simulated street-level weather stations (AWS), and
6. drafts plain-language advisories for four audiences, which a named human reviewer must approve before they count as sent.

Everything is delivered as an interactive **Streamlit** dashboard. Because real IMD grid files and AWS feeds were not
available, the database is generated by code in this repository, so the whole study is reproducible with two commands.

### Objectives (from the use case) and where they are met

| Use case objective | Where in this project |
| --- | --- |
| Analyse spatio-temporal temperature patterns by region and season | Regional Analytics page; 7 regions, 4 IMD seasons, spells and trends, 2005-2026 |
| AI models for Tmax forecasting, heatwave prediction, hotspot identification, severity classification | `hw/models.py`; Tmax regressors, severity classifier, risk index, Hotspot Map |
| IoT-enabled AWS for local monitoring and forecast validation | AWS Monitoring page; 40 simulated stations with hourly data and device health |
| Visualisation, decision support and early warning | Eight-page dashboard, alert board, advisories with human approval |

### Key features

- **7-day probabilistic forecast** per city: Tmax, 90% range, class probabilities, risk index and alert tier.
- **Issue-date control:** pick any date from 2024 onward; the system sees only data up to that evening, so past dates behave like live operation. A "Peak 2026 heat" button jumps to 14 May 2026.
- **Verification mode:** reveal what actually happened next to each forecast.
- **What-if simulator:** nudge recent temperature, humidity or the upper-air ridge in one city and watch the forecast and alert change.
- **Hotspot detection:** an interpolated heat surface plus automatic clusters (DBSCAN) of cities at Orange or Red.
- **AWS layer:** station map, urban heat island comparison, forecast versus ground truth, battery/signal/uptime health and quality-control flags.
- **Advisories:** drafts for citizens (English, Hindi, Marathi), farmers, health agencies and municipal/disaster authorities, a number-consistency check, a reviewer approval form and a downloadable decision log.
- **Model Lab:** skill against baselines by lead time, reliability, confusion matrix, alert-threshold selection, feature importance and a case-study viewer.

## Data

Everything is generated by `hw/datagen.py` with fixed random seeds.

- **Daily archive:** 79,490 city-days (10 cities, 1 Jan 2005 to 6 Oct 2026) with Tmax, Tmin, afternoon humidity, wind and an upper-air ridge index (a synthetic stand-in for the 500-hPa height anomaly).
- **How it is generated:** smooth seasonal cycle per city, correlated AR(1) weather noise, a warming trend (0.035 C per year), regional heatwave events with a Gaussian footprint (neighbouring cities heat together), small local events, and a ridge index that builds 3 to 8 days before most regional events (about a quarter of ridges under-deliver).
- **Deliberate defects:** a raw copy has 99.9 missing-value codes, blanks, isolated spikes, swapped Tmin/Tmax, impossible humidity, missing days and duplicate rows. The cleaning pipeline repairs them (mean error on repaired Tmax values: 0.75 C).
- **AWS feed:** 40 stations (4 per city: urban core, industrial, suburban, green belt), 618,240 hourly readings from 1 Jan 2025, with battery voltage, signal strength, outages and a few sensor spikes. Quality control flags each reading as OK, out of range, spike or missing.

### Time split
Training 2005-2022, validation 2023, hold-out test 2024 onward (never seen in training).

## Methodology and algorithm

**1. Heatwave classification (IMD-style rules).** With departure d = Tmax minus the day-of-year normal:

| Class | Plains | Coastal |
| --- | --- | --- |
| 1 Hot day | Tmax >= 40 C and d >= 3.0 C | Tmax >= 37 C and d >= 3.0 C |
| 2 Heatwave | Tmax >= 40 C and d >= 4.5 C, or Tmax >= 45 C | Tmax >= 37 C and d >= 4.5 C |
| 3 Severe heatwave | Tmax >= 40 C and d >= 6.5 C, or Tmax >= 47 C | Tmax >= 37 C and d >= 6.5 C |

IMD declares a heatwave after two consecutive days; this project classifies single days and reports multi-day spells separately.

**2. Features.** 52 predictors from information available that evening: recent departures and rolling statistics, Tmin, humidity, wind, heat index, hot/heatwave streaks, the ridge index and its changes, the same signals from neighbouring cities (inverse-distance weighted) and across the network, season, location, and the normal for the target day. The classifier also receives the lead time.

**3. Models.**
- *Tmax regressors:* one gradient-boosting regressor per lead time (1 to 7 days) predicts the departure from normal. A 90% range comes from validation-year error percentiles by lead time and season.
- *Severity classifier:* one gradient-boosting classifier trained on all seven lead times stacked.
- *Blend:* cumulative class probabilities from the classifier are averaged with probabilities derived from the regression forecast and its error spread, then converted back to class probabilities.

**4. Risk index and alerts.**
`HRI = 100 x (0.25 p1 + 0.65 p2 + 1.00 p3)`
Alert tier for a day: Red if P(severe) >= 15%; Orange if P(heatwave or worse) >= 20%; Yellow if P(hot day or worse) >= 25%; otherwise Green. A city's tier is the worst day in the look-ahead window. Thresholds were read off the flat top of the CSI-versus-threshold curves on the validation year and rounded.

**5. Hotspots.** DBSCAN (700 km, haversine distance, at least 2 cities) on cities at Orange or Red.

**6. Advisories.** A deterministic template engine drafts text from a facts pack (Tmax, range, probabilities, lead time, hottest AWS station). Every number in the draft is checked against the facts. A reviewer approves, holds or rejects, and the decision is logged.

```text
Every evening, for each city:
  1. clean the day's observations (range, spike and missing checks)
  2. build the 52 predictors from the recent record and neighbouring cities
  3. for h = 1..7: predict Tmax departure -> forecast and 90% range
  4. classify severity -> blend with the regression-based probabilities
  5. compute HRI and the alert tier for each day
  6. city tier = worst day in the look-ahead window; record first alert day
  7. collect a facts pack, draft an advisory per audience from the facts only
  8. check every number in the draft against the facts pack
  9. a named reviewer edits, approves or rejects; log the decision
```

## Results (hold-out period, 1 Jan 2024 to 6 Oct 2026)

1,010 forecast days, 10 cities, 124 actual heatwave city-days. These describe the synthetic data, not real-world performance.

| Lead (days) | Tmax MAE (C) | Persistence-of-anomaly MAE (C) | Heatwave AUC | Alert CSI (Orange+) | Persistence CSI |
| --- | --- | --- | --- | --- | --- |
| 1 | 0.82 | 0.87 | 0.99 | 0.41 | 0.40 |
| 3 | 1.15 | 1.35 | 0.96 | 0.24 | 0.18 |
| 5 | 1.25 | 1.53 | 0.95 | 0.16 | 0.10 |
| 7 | 1.29 | 1.62 | 0.92 | 0.07 | 0.07 |

- The Tmax forecast beats the "today's anomaly persists" baseline at every lead time; the advantage grows from 6% at 1 day to 20% at 7 days.
- Heatwave probabilities beat climatology up to about day 5 and have no skill by day 7. At 1 day the model is only on par with persistence.
- Pooled over days 1 to 3: Orange or higher catches 45% of heatwave days with 48% of alerts false; Red catches 22% of severe days with 58% false alarms.
- On days that actually were heatwaves the forecast runs 1.7 to 4.7 C too cool.
- Urban-core AWS stations read about 1.5 C hotter than the city record and find three times as many heatwave days; green-belt stations read about 0.8 C cooler.
- The 90% forecast range covers 86 to 89% of outcomes.

A full project report (aim, methodology, algorithm, results) accompanies this repository.

## Troubleshooting

- **"Data and models have not been built yet":** run `python scripts/build_all.py` then `python scripts/evaluate.py`, and refresh.
- **Old styling or layout glitches after updating:** stop Streamlit, restart it, and hard-refresh the browser (Ctrl+Shift+R).
- **Maps are blank:** the base-map tiles need internet access.
- **Port already in use:** `streamlit run app.py --server.port 8502`.

## Limitations

- All data are synthetic, so skill figures describe the simulation. The ridge index was built to lead events by 3 to 8 days; real forecasts would need numerical weather model output or reanalysis fields.
- The generator was tuned during development (adding the ridge precursor, reducing purely local events) because the first version gave heatwaves no warning signs.
- Detection is weak at the extremes: Red alerts miss most severe days, forecasts run cool on actual heatwave days, and there is no heatwave skill at 6 to 7 days.
- Alert thresholds were set on one validation year with few severe events, and the hold-out has only 124 heatwave city-days, so skill estimates are noisy.
- AWS sites and city climate figures are illustrative, not real stations or published normals.

## Responsible AI
Forecasts are shown as probabilities with ranges and a confidence label by lead time, and known weaknesses are stated on screen.
Advisory numbers are checked against the forecast facts, and no advisory counts as sent until a named reviewer approves it and the decision is logged.
The decision log stores reviewer names only; restrict access to it in any real deployment.

## Future scope

3. Add numerical weather model fields as predictors for lead times beyond 3 days.
4. Retrain automatically as new observations arrive, with drift monitoring.
5. Choose AWS sites from the hotspot analysis and add ward-level maps for municipal action plans.
